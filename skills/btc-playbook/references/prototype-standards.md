# Prototype standards

## What it is judged on now
Having a prototype stopped being a differentiator; most submissions include one.
1. **Legibility in ~90 seconds.** A reviewer opens the link with no context. Can they tell what
   it is, who it is for, and what to do first?
2. **Novelty × completeness.** Competent prototype of an obvious idea = middle of the pile.
   Stand out with an idea the reviewer hasn't seen, or an execution that goes further (one flow
   truly finished, including states others skip). Novelty without completeness reads as a sketch.

If the brief asks for a deck AND a prototype, the deck still carries the argument: a beautiful
prototype on a thin deck reads worse than a strong deck with a rough prototype. If the prototype
IS the deliverable, it must carry the argument alone.

## Deck decision → interface
A deck can state a decision in one sentence; a prototype must render it. Unspecified details get
invented generically. A build prompt must name: **screens, the primary action on each, the data
shown, the states, and the one path the reviewer should walk.**

## Build rules
1. **One golden path, complete**: entry → flow → key action → visible result.
2. **Match fidelity to purpose**: hi-fi golden path + low-fi supporting screens is legitimate. If
   wireframes were asked, a polished app is not extra credit.
3. **Realistic, internally consistent data** (Indian names, ₹ prices, believable timestamps).
4. **In-app guidance for a first-time evaluator**: entry screen saying what this is and what to
   try, a short first-load walkthrough, a visibly suggested path, labelled demo data.
5. **Real states if time allows**: empty, loading, error, new user with no history.
6. **Verify hosting**: incognito, logged out, phone + laptop; no login/signup wall; link in the
   deck on an early slide; keep a recorded walkthrough or screenshot appendix as backup.

## Design bar
Not evaluated on design, but bad design derails a good case. Clear the bar, then stop:
navigation, buttons, forms, cards, tables, modals, empty states, loading indicators present and
**consistent** (one button style, one spacing scale). Marginal effort pays in: error states,
one well-placed hint where users hesitate, onboarding/suggested path, realistic data.
Order: finish the golden path BEFORE any state polish.

## Time rule
Half-day pre-interview case: an optional prototype usually doesn't fit. Don't thin a required
section to build one. Get to a hosted link within the first couple of hours when it IS required.
